# SOCIAL-011 历史内容清理与备份恢复方案（未在生产执行）

仅有既有权限已经明确的全局撤回/彻底删除记录可列入本方案；`deleted=0`的个人副本删除不能据此清除所有人正文。阅后即焚时间规则、接收者范围未定，不能回填猜测的expires_at或扫描旧消息年龄批量删除。

1. 在受控隔离环境用合成SQLite/文件建立删除前快照，验证权限墓碑、正文、编辑事件、文件引用和统计。生产数据若另行获授权迁出，也不得在报告展示正文；本轮只使用合成数据。
2. 干跑只输出按状态聚合数量，不输出正文、Token或用户私信。仅对既有deleted=1/2清content/file_url及关联conversation_events.payload；事务内处理，分批、游标和重试需在未来正式运维实现中加入。绝不包含个人user_message_deletions对应deleted=0行。
3. 故障记录只保留任务标识、阶段、错误码和数量。失败事务回滚；重试与再次运行不扩大范围。已删除消息在访问层先拒绝，不能依赖清理完成才拒绝。
4. 附件先按可信file_registry/file_registry_shares及所有仍合法消息引用计数。任一合法引用存在则保留；零引用资源还需核对缩略图、对象存储、CDN与已发URL撤销方式后另行清理。本轮不执行物理资源删除。
5. 新全局删除会清事件payload；旧已deleted=2的请求可能幂等早退，不能把重复旧请求当作历史回填任务。
6. 恢复备份时网络入口保持关闭；重放比快照新的删除/撤权记录及正式批准的服务器期限规则后，逐API验证不会返回受限正文，再允许开放。缺少新墓碑日志/可信期限时，不能证明旧快照安全；保留恢复阻断，不先上线等后台慢清。
7. SQLite逻辑字段清空不等于磁盘安全擦除，WAL、freelist、快照、运维日志仍有独立保留边界。备份脚本源码默认30天不代表生产已启用该周期。记录访问截止、主库清理完成、对象清理完成、备份轮转完成等不同时间，禁止用一个“删除成功”替代全部。

实际演练：`tools/historical-cleanup-rehearsal.py` 不接受外部数据库路径，只在本轮tmp中新建合成SQLite。5项通过：故障回滚、重试+幂等、合法数据保留、重新打开数据库状态保持、旧备份仍含旧数据的负例。证据 `evidence/historical-cleanup-rehearsal.json`。**这是SQL方案验证，不是产品清理worker、服务自动到期、正式备份恢复门禁或生产迁移通过。**
