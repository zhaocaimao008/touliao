## 一、核心原理

Web / 桌面端 / Android / iOS 四端启动时都走同一套**三层优先级**机制去决定连哪个后端
（代码见 `web/src/utils/config.js`、`desktop-electron/src/main.js:129-131`、
`android/.../core/config/RemoteConfig.kt:66-67`、`ios/.../Core/Config/RemoteConfig.swift:15-16`）：

```
手动覆盖（用户在登录页/设置里填的，本地持久化） > 运行时拉取的 config.json > 编译内置默认值
```

手动覆盖一旦设置，不会被后两者覆盖，且**都不需要重新编译打包 App 就能换后端地址**。

**和 vxin 不一样的地方**：vxin 是把 `config.json` 放在独立的 `vxin-config` 仓库、经 CDN
（`cdn.jsdelivr.net`）分发，一个 GitHub Actions workflow 点一下就能全端切换。**touliao 目前
没有这套独立配置仓库+CDN机制**——四端的引导地址（`CONFIG_URLS`）直接硬编码指向
`https://touliao.cc/config.json`（+`www`子域兜底），`config.json` 就放在 touliao.cc 自己的
服务器上，跟后端、前端静态资源同源。这意味着：

- **换"官方 touliao.cc 背后的实际服务器"**：只需要在当前 touliao.cc 所在的服务器上编辑/替换
  `config.json` 内容并让 nginx 继续按原样提供这个静态文件即可，全端下次启动会自动读到新值
  （Web端Ping超时800ms/Electron和移动端必须等到完整config，见`config.js`注释）
- **全新私有化部署客户（自己的域名，不是touliao.cc）**：四端出厂默认值仍然指向`touliao.cc`，
  客户拿到的全新安装App**首次启动会先尝试联系touliao.cc**。客户要么让终端用户在登录页手动
  "切换服务器"填一次自己的域名（一次性操作成本，之后走localStorage/UserDefaults/SharedPreferences
  持久化，不会再变回touliao.cc），要么单独出一版改了`CONFIG_URLS`默认值的定制构建。详细分析见
  `AUDIT.md` 第十六节第1点。

## 二、全新服务器上把后端跑起来

```bash
git clone https://github.com/zhaocaimao008/touliao.git
cd touliao
bash deploy/setup-new-server.sh https://你的域名.com 你的邮箱@xx.com
```

**用 `setup-new-server.sh`，不要用 `deploy/setup.sh`**——`setup.sh` 更简单但有个已知缺口：
不会生成 `ADMIN_USERNAME`/`ADMIN_PASSWORD`，而生产环境启动时这两个变量缺失会直接
`process.exit` 致命报错，跟着 `deploy/README.md` 走这一步会踩坑（`AUDIT.md`第十六节第2点已记录，
截至写这份文档还没修）。`setup-new-server.sh` 正确处理了这个问题：自动生成随机管理员密码，
写入 `.env` 并另存一份 `backend-v2/ADMIN_PASSWORD.txt`（`chmod 600`）。

脚本自动完成：装依赖 → 生成随机 `JWT_SECRET`/管理员密码写 `.env` → pm2 启动后端
（进程名 **`touliao-backend`**，监听 **`127.0.0.1:3003`**，见 `backend-v2/ecosystem.config.js`——
注意 `deploy/README.md` 里那张环境变量表把默认端口写成了3002，跟`ecosystem.config.js`里
实际的3003不一致，这是那份文档自己的笔误，请以`ecosystem.config.js`为准）→ 构建前端并部署
→ 配 nginx（反代 + WebSocket + 前端托管）→ 申请 HTTPS 证书。

可选环境变量（命令前加 `KEY=val`）：`ALERT_BOT_TOKEN`/`ALERT_CHAT_ID`（Telegram告警）、
`SENTRY_DSN`、`ADMIN_IP_WHITELIST`（留空=自动检测当前SSH IP）。

通话要能接通需要装 coturn：`backend-v2/docs/COTURN_SETUP.md`。

> 之后日常更新：`git pull && pm2 restart touliao-backend`。

## 三、拿 Android APK

**实际机制**（`.github/workflows/android-release.yml`）：CI 用仓库 Secret
`ANDROID_KEYSTORE_BASE64`/`ANDROID_KEYSTORE_PASSWORD`/`ANDROID_KEY_ALIAS`/`ANDROID_KEY_PASSWORD`
（已配置，2026-08-28写入）解码出 `touliao-release.jks` 到 CI 运行时临时目录签名打包——
**这把签名私钥不落地在任何服务器的本地磁盘**，只以 GitHub Secret 形式存在，构建完临时文件
随 runner 销毁，这点比 vxin 手册里"钥匙放在服务器 `/root/vxin-release-keystore/` 本地目录"的
做法更安全（不存在"服务器被入侵=钥匙被偷"的单点风险）。

打包完成后，CI 设计上会：
1. 把签名APK作为 GitHub Actions Artifact 上传（名字 `touliao-release-apk`）——**这一步稳定可用**
2. 尝试 `scp` 部署到 `/var/www/touliao-downloads/touliao-android-latest.apk`（供App内自动更新用），
   同步生成 `touliao-android-version.json`

**但第2步目前实际跑不通**：这一步依赖的 `secrets.DEPLOY_SSH_KEY`/`DEPLOY_USER`/`DEPLOY_SERVER_HOST`
**没有配置**（`gh secret list` 确认，2026-08-30核实），跟`AUDIT.md`第十七节第4点记录的
`deploy.yml`后端自动部署同一个系统性问题一样——job本身不会因此报错阻断（无`continue-on-error`
硬性保证，需要实测确认失败表现），但 `https://touliao.cc/downloads/touliao-android-latest.apk`
**不会被这条流水线自动更新**。

**实际能拿到 APK 的办法**：GitHub 仓库 → Actions → 选中 `Android Release APK` workflow 的某次
运行 → 底部 Artifacts → 下载 `touliao-release-apk`（zip，解压得`.apk`，首次安装需允许"未知来源"）。

App 内"检查更新"读的是 `UpdateChecker.kt` 里硬编码的
`https://touliao.cc/downloads/touliao-android-version.json`——只要这个文件没有被第2步自动同步，
线上用户就拉不到新版本提示，**发布新版本后需要人工确认这个JSON是否已经更新**，不能假设CI会自动搞定。

安装前的完整性防护：`ApkInstaller.kt` 会比对待安装APK的签名证书SHA256指纹与当前已安装App的指纹，
不一致直接拒装（见 `AUDIT.md` 第十七节第6点），这道防线独立于上面第2步是否跑通，随时生效。

## 四、iOS

iOS 走标准 App Store / TestFlight 分发，仓库里**没有任何自建更新通道**（`ios-testflight.yml` +
已配置的 `ASC_API_KEY_BASE64`/`ASC_ISSUER_ID`/`ASC_KEY_ID`/`IOS_CERTIFICATE_P12_BASE64`等Secret，
2026-08-25/29写入）。要装到真机/上架需要 Apple 开发者账号（$99/年）+ 对应证书/描述文件，
签名细节见 `docs/IOS_SIGNING_SETUP.md`。

## 五、桌面端（Windows / Mac / Linux）

`desktop-electron/` 用 `electron-builder` 打包，发布地址固化在
`desktop-electron/package.json` → `build.publish.url = https://touliao.cc/downloads/updates`。

```bash
cd desktop-electron
npm run build:win   # 或 build:mac / build:linux
```

**自动更新完整性校验现状（截至2026-08-30）**：`electron-updater` 关闭了内置的Windows代码签名校验
（`autoUpdater.verifyUpdateCodeSignature` 被显式stub成永远通过——因为目前压根没有代码签名证书，
见`SECURITY-RELEASE.md`的P0未解决项）；额外的 Ed25519 元数据二次验签机制**代码已实现但尚未启用**——
`src/update-public-key.pem` 还是生成脚本留的占位文本，没有真实密钥对，效果等同于这道防线完全没生效。
启用步骤、风险分析见 `AUDIT.md` 第十七节第8点。**在启用之前，不要假设桌面端更新包的完整性有除
TLS之外的任何额外保护。**

## 六、签名密钥保管一览

| 密钥 | 用途 | 当前保管方式 | 状态 |
|---|---|---|---|
| `touliao-release.jks` | Android APK 签名 | GitHub Secret（`ANDROID_KEYSTORE_BASE64`等4项），不落地服务器本地明文 | 已配置，CI 可正常打包 |
| Apple 证书/描述文件/ASC API Key | iOS TestFlight 签名 | GitHub Secret（`IOS_CERTIFICATE_*`/`ASC_*`等） | 已配置 |
| Ed25519 更新元数据签名私钥 | 桌面端 latest.yml 二次验签 | 尚未生成（`update-public-key.pem`仍是占位文本） | **未启用**，见 `AUDIT.md` 十七.8 |
| Windows/macOS 代码签名证书 | 桌面端安装包发布者签名 | 尚未采购/配置 | **未启用**，见 `desktop-electron/SECURITY-RELEASE.md` P0 |

> ⚠️ Android 签名私钥目前只以 GitHub Secret 形式存在——**请确认是否有这份 `.jks` 原始文件的离线
> 备份**（密码管理器/HSM/加密介质）。如果 GitHub Secret 是唯一副本，一旦这个仓库的 Secret 被
> 误删或账号出问题，将无法再给已发布的 App 出签名一致的升级包，老用户只能卸载重装。这不是
> "已发生的问题"，是一条需要主动确认的运维检查项。

## 七、常见问题

- **改了 `config.json` 但 App 还连旧服务器？** Web端有800ms超时+localStorage缓存，Electron/移动端
  会等到拿到完整config才继续，正常情况下重启App即可生效；如果服务器本身没起来会一直用缓存/兜底值。
- **想临时连某台服务器调试？** 登录页/设置里都有"切换服务器"，手动输入的地址优先级最高，
  不会被远程config覆盖。
- **私有化部署给新客户，出厂默认值要连touliao.cc吗？** 见第一节最后一段——目前只能接受"首次
  需要手动填一次服务器地址"，或者单独出一版改了`CONFIG_URLS`默认值的构建，产品侧需要明确选哪种。
- **网页前端换服务器要重新部署吗？** 不需要——`VITE_API_BASE`留空，Web端用同源相对路径，
  部署到哪个域名就连哪个，这条和vxin原来的说法一致，touliao这块没变。
