## 为什么模拟测试不能替代真机测试

Playwright 的设备模拟只改变了三件事：视口尺寸、User-Agent 字符串、以及是否派发触摸事件（`hasTouch`）。它**不能**复现以下真机才有的行为差异：

- 真实的移动 GPU 渲染管线、内存/CPU 限制、低端机型的卡顿
- iOS Safari / Android WebView 与桌面 Chromium/WebKit 内核之间的真实差异（移动 Safari 并非桌面 WebKit 的简单缩放）
- 原生键盘弹出对视口高度的挤压（iOS `visualViewport` 行为、Android 软键盘 resize/pan 模式）
- 系统级手势冲突（下拉刷新、边缘返回手势、系统通知栏遮挡）
- 移动网络切换（WiFi ↔ 4G/5G ↔ 弱网）下的 WebSocket 重连行为
- 电池优化/后台进程冻结对长连接、推送到达的影响
- 真实摄像头/相册权限弹窗、文件选择器的原生 UI
- App 内嵌 WebView（如有）与浏览器 WebView 内核版本差异
- 触觉反馈、原生滚动惯性（momentum scrolling）与浏览器模拟滚动的手感差异

## 待真机验证条目

### 基础功能
- [ ] iOS Safari（真机，非模拟器）：登录 / 收发消息 / 已读收据 / 撤回 / 群聊 / 退出登录
- [ ] Android Chrome（真机）：同上全流程
- [ ] 如有原生 App 壳（Capacitor/Electron 移动端），App 内 WebView：同上全流程

### 键盘与输入
- [ ] 点击消息输入框后，原生键盘弹出，聊天窗口是否正确上推、输入框和发送按钮是否始终可见
- [ ] 长文本输入时输入框是否正确换行/滚动，不遮挡发送按钮
- [ ] 表情选择器与键盘切换时是否有布局跳动（layout jump）

### 手势与导航
- [ ] iOS 边缘左滑返回手势是否与应用内“返回”按钮冲突
- [ ] Android 系统返回键是否正确关闭聊天窗口/子页面而非直接退出 App
- [ ] 下拉刷新（如有）是否与浏览器/系统下拉刷新手势冲突
- [ ] 长按消息呼出右键菜单（撤回/复制等）在触屏上的触发是否灵敏、误触率如何

### 网络与实时性
- [ ] 真实 4G/5G 网络下 WebSocket 连接建立时间、消息延迟
- [ ] 切换 WiFi ↔ 蜂窝网络时，WebSocket 是否正确重连，消息是否丢失
- [ ] 弱网/丢包环境下发送消息的重试与失败提示
- [ ] App 切到后台数分钟后再切回前台，消息是否正确补发/同步

### 系统集成
- [ ] 锁屏通知/推送到达（如已配置推送服务）
- [ ] 相机/相册权限弹窗的原生交互，拍照发图/选图发送全流程
- [ ] 文件发送（原生文件选择器）
- [ ] 来电铃声开关等设备权限相关设置项（首页顶部横条提到的"来电铃声提醒"功能）的真实交互

### 性能与稳定性
- [ ] 中低端机型（如 4GB 内存及以下 Android 机）上长时间使用（30 分钟+）是否有卡顿、内存增长
- [ ] 历史消息滚动加载在真机上的流畅度（模拟环境的性能特征不代表移动 GPU/CPU 实际表现）
- [ ] 电池消耗（长连接 WebSocket 常驻是否显著耗电）
